# Windows の APO の仕組み

Windows には、再生や録音の音に効果をかける部品を差し込む仕組みがあります。この部品を APO（Audio Processing Object）と呼びます。PRI System Rack は、この仕組みを使ってシステム全体の再生音を VST3 プラグインに通しています。

この文書では、APO がどこで動き、どう登録され、何を守る必要があるかを説明し、そのうえで PRI System Rack の APO がどう動くかを説明します。

## APO とは

- APO は COM のオブジェクトで、DLL に入っています。Windows Vista から使われています。
- Windows のオーディオエンジン（`audiodg.exe`）が APO の DLL を読み込み、自分のプロセスの中で動かします。
- もとはサウンドデバイスのメーカーが、そのデバイス専用の効果（スピーカーの補正、イコライザー、ラウドネスなど）を入れるための仕組みです。ドライバーや Windows のバージョンによっては、サウンドの設定画面のデバイスのプロパティに「拡張」タブが出て、そこで効果を切り替えられます（今の Microsoft の文書は、メーカー独自の設定画面にはハードウェアサポートアプリを使うよう勧めています）。

## 再生の音の流れ

```
アプリ A ─┐
アプリ B ─┼─ Windows のオーディオエンジン（audiodg.exe） ─→ ドライバー ─→ サウンドデバイス
アプリ C ─┘        │
                   └ ここで APO が音を処理する
```

- 普通のアプリは共有モード（WASAPI の shared mode）で音を出します。オーディオエンジンが各アプリの音を 1 つにまとめ（ミックス）、デバイスに送ります。
- APO はこの途中に入ります。アプリの音ごとに処理する枠と、まとめた後の音を処理する枠があります（次の節）。
- 排他モード（WASAPI の exclusive mode）や ASIO で出した音は、オーディオエンジンのミックスを通らずにドライバーへ届くので、APO を通りません。

## APO を入れる枠

APO は、音の流れのどこで処理するかを決めた「枠」に入れます。どの枠に入れるかは、再生デバイスごとにレジストリで指定します（「デバイスへの登録」の節）。

今の Microsoft の文書は、次の 3 つの枠で説明しています。

| 枠 | 正式な名前 | 処理する位置 |
| --- | --- | --- |
| SFX | Stream effect | ミックスの前。アプリの音（ストリーム）ごとに 1 つずつ作られる |
| MFX | Mode effect | 同じモード（次の段落）のストリームをまとめた後、すべてのモードをまとめる前 |
| EFX | Endpoint effect | すべてのモードをまとめた後。そのデバイスに出る音すべてにかかる |

- モード: ストリームには、その音の使い道（既定、通話、映画、音楽、RAW など）を表すモードがあります。デバイスは、モードごとに別の効果をかけられます。
- RAW モードは「何も加工しない音」を求めるモードです。Microsoft の文書によると、RAW のストリームには SFX がかからず（Windows 10 では RAW の MFX は読み込まれる）、EFX は RAW のストリームにも必ずかかります。
- Composite の枠（次の表）を除き、1 つのデバイスには枠ごとに 1 つの APO しか入れられません。同じ枠に別の APO を入れると、前の APO は外れます。

ほかに、次の枠もあります。

| 枠 | 内容 |
| --- | --- |
| LFX | 古い形の枠。ミックスの前（SFX に近い位置） |
| GFX | 古い形の枠。ミックスの後（PRI System Rack はここに入る） |
| Composite SFX / MFX / EFX | 1 つの枠に複数の APO を並べて入れられる形（Windows 10 バージョン 1803 から） |
| UI | APO ではなく、「拡張」タブの設定画面を出す部品を指定する |

古い形の枠（LFX / GFX）は、同じデバイスに SFX / MFX / EFX のどれかが入っていると使われません（Microsoft の文書には書かれておらず、システム全体に効果をかける APO の開発者が公開している資料による）。

## デバイスへの登録

APO を使えるようにするには、2 つの登録が要ります。

1. **APO そのものの登録**: DLL を COM のオブジェクトとして登録します（`HKLM\SOFTWARE\Classes\CLSID\{APO の CLSID}`）。あわせて、APO の一覧（`HKLM\SOFTWARE\Classes\AudioEngine\AudioProcessingObjects`）にも登録します。
2. **再生デバイスへの割り当て**: 再生デバイスごとのキー `HKLM\SOFTWARE\Microsoft\Windows\CurrentVersion\MMDevices\Audio\Render\{デバイスの GUID}\FxProperties` に、枠ごとの値として APO の CLSID を書きます。

APO の CLSID を入れる主な値の名前は、`{d04e05a6-594b-4fb6-a80d-01af5eed7d1d},<番号>` の形です。番号は次のとおりです（FxProperties には、ほかにも効果の名前や対応するモードの一覧などの値があります）。

| 番号 | 枠 |
| --- | --- |
| 1 | LFX |
| 2 | GFX |
| 3 | UI |
| 5 | SFX |
| 6 | MFX |
| 7 | EFX |
| 13〜15 | Composite SFX / MFX / EFX（CLSID の並び） |

- 普通は、サウンドデバイスのドライバーをインストールするときに、ドライバーの設定ファイル（INF）がこの登録を行います。Windows 10 バージョン 1809 からは、ドライバーと一緒に入れる APO は、ドライバーごとに自分の APO を登録する形（componentized）が求められています。
- システム全体に効果をかけるツールは、ドライバーとは別に、上の 1 の場所に APO を登録し、FxProperties を直接書き換えて APO を割り当てます。PRI System Rack もこの方法で、Windows 10 22H2 で読み込まれることを確かめています。
- FxProperties は `HKLM` にあるので、書き換えるには管理者の権限が要ります。
- 書き換えた後は、Windows Audio のサービス（`Audiosrv`）を起動し直すと、新しい APO が読み込まれます（PC の再起動は要りません）。起動し直す間、数秒ほど Windows の音が止まります。

## 署名と保護された環境

- オーディオエンジンは保護された環境で動き、条件を満たさない APO は読み込みません。
- `HKLM\SOFTWARE\Microsoft\Windows\CurrentVersion\Audio` の `DisableProtectedAudioDG` を 1 にすると、この保護が弱まり、署名のない APO も読み込まれます。Microsoft の文書では、開発やテストのための設定として扱われています。1 にすると、保護されたコンテンツ（著作権保護のかかった動画など）の再生に失敗することがあると報告されています。
- Microsoft の文書によると、APO の作成や準備（形式の確認、`LockForProcess`）が続けて 10 回失敗すると、Windows はそのデバイスの効果（「拡張」）を無効にします（途中で成功すれば数え直します。文書は SFX / MFX / EFX について書いています）。

## APO の中で守ること

オーディオエンジンは、APO のメソッドをおおよそ次の順に呼びます。

```
Initialize                        どのデバイスのどの枠で使われるかを受け取る
IsInputFormatSupported など       音の形式（チャンネル数、サンプリング周波数など）を決める
LockForProcess                    処理を始める前の準備
APOProcess（周期ごとに繰り返す）  音を処理する
UnlockForProcess                  処理の終わり
```

- `APOProcess` は、オーディオエンジンのリアルタイムのスレッドから、決まった周期で呼ばれます。周期はデバイスによって変わります。開発に使った環境（Windows 10 22H2、48 kHz・2ch）では、1 回 480 フレーム（10 ms）でした。
- Microsoft の文書は、リアルタイムに呼ばれるメソッドについて「止まって待たないこと（ブロックしない）、ページングされるメモリーを使わないこと、待つ可能性のあるシステムの処理を呼ばないこと」を求めています。実際には、メモリーの確保、ロック、ファイルの読み書き、ログの書き出しなどを `APOProcess` の中で行わないことになります。
- 1 回の処理が周期に間に合わないと、そのデバイスに出るすべての音が途切れます。APO は `audiodg.exe` の中で動くので、APO が落ちると `audiodg.exe` ごと落ち、そのデバイスの音が途切れます。
- `audiodg.exe` はサービスとして、ユーザーのデスクトップとは別のセッション（セッション 0）で動きます（開発に使った環境では LOCAL SERVICE のアカウントで動いていました）。APO の中から画面を出すことはできません。
- オーディオエンジンは APO を COM の集約（aggregation）で作ります。集約に対応していない APO は動きません。

## APO の中でプラグインを動かさない理由

VST3 プラグインを APO の中（`audiodg.exe` の中）で直接動かすと、次の問題が起きます。

- プラグインの画面を出せない（デスクトップとは別のセッションで動くため）。
- プラグインが落ちると、オーディオエンジンごと落ち、そのデバイスの音がすべて途切れる。
- プラグインはユーザーのフォルダーや認証の仕組みを使うことが多いが、サービスのアカウントではそれらが使えない。
- 処理が重いプラグインが周期に間に合わないと、すべての音が途切れる。

そこで PRI System Rack は、APO には「音を本体アプリに渡して、処理結果を受け取る」ことだけをさせ、プラグインは本体アプリ（ユーザーのデスクトップで動く普通のプロセス）で動かします。

## PRI System Rack の APO

```
各アプリの音 → オーディオエンジン（audiodg.exe）のミックス → GFX の枠 → サウンドデバイス
                                                              │ ↑
                                                      共有メモリ（音の受け渡し）
                                                              ↓ │
                                               本体アプリ（VST3 を順に処理。画面も出す）
```

### 入れる場所

- 再生デバイスの GFX の枠（ミックスの後）に入れます。すべてのアプリの音をまとめた後の音を 1 回だけ処理するので、アプリがいくつ鳴っていても処理は 1 系統です。
- 入れる・外すのは補助プログラム `PRISystemRackSetup.exe`（管理者の権限で動く）が行います。本体アプリの［有効］［無効］で呼び出します。
- ［有効］にするときは、そのデバイスの FxProperties にある APO の値すべて（LFX、GFX、UI、SFX、MFX、EFX、Composite の各枠）と効果の名前を、`HKLM\SOFTWARE\PRISystemRack\EndpointBackup\{デバイスの GUID}` に控えてから外します。ほかの APO が入っていなくても控えを作ります。GFX の枠は SFX / MFX / EFX のどれかが入っていると使われないので、メーカーのドライバーが入れた効果（スピーカーの補正など）も［有効］の間は外れます。
- ［無効］にすると、控えた値を書き戻して控えを消します。ただし、［有効］にした後で別のツールが書き換えていて、控えと違う値が入っている枠は、今の値を残します。

### 本体アプリとの受け渡し

- APO は `Initialize` で渡されたデバイスのプロパティからデバイスの GUID を読み、`LockForProcess` で、その GUID を名前に入れた共有メモリと 2 つのイベントを作ります（例: `Global\PRISystemRack.v1.Memory.{デバイスの GUID}`）。本体アプリは同じ名前で開きます。
- `audiodg.exe` と本体アプリは別のアカウント・別のセッションで動くので、名前は `Global\` に置き、ログオンしているユーザーが読み書きできるようアクセス権を付けます。
- 1 周期の流れ:
  1. APO が入力の音を共有メモリに書き、番号を 1 つ進めて、本体アプリに知らせる（Request イベント）。
  2. 本体アプリがプラグインで処理し、結果を共有メモリに書いて、APO に知らせる（Response イベント）。
  3. APO は結果を出力に写す。
- APO は `APOProcess` の中で、本体アプリの結果を周期の 60% まで（10 ms の周期なら 6 ms）待ちます。これは前の節の「ブロックしない」という決まりから意図して外れている部分です。待つ時間に上限を設け、間に合わなければその周期は処理せずに元の音をそのまま流す（素通し）ことで、音が途切れないようにしています。
- 本体アプリは、APO からの知らせを待つ合間（最大 0.1 秒）ごとに「動いている」印（心拍）を書きます。心拍が 0.5 秒より古ければ、APO は本体アプリがいないとみなし、待たずに素通しにします。本体アプリを正常に終えたときは、終わる前に APO へ知らせるので、すぐ素通しになります。本体アプリが落ちても、音は止まりません。
- 無音の周期も本体アプリに渡します。リバーブの残響やアナライザーの表示が途切れないようにするためです。
- `APOProcess` の中では、共有メモリへの読み書きとイベントの待ち合わせだけを行い、メモリーの確保やログの書き出しはしません。

### 遅延

- 処理結果は同じ周期のうちに返すので、APO を通すことで遅延は増えません（増えるのはプラグイン自身のレイテンシーと、本体アプリの処理バッファを使ったときのその分だけです）。
- 開発中の測定（2026-11-03、Windows 10 22H2）では、受け渡しの往復は平均 23 µs、最大 162 µs でした（テスト用のホストで、プラグインの処理を含まない値）。

## 気を付けること

- 排他モードや ASIO で出した音は APO を通らないので、PRI System Rack のプラグインもかかりません。
- ［有効］にしている間は、そのデバイスのほかの APO（メーカーのドライバーが入れた効果を含む）はすべて外れています。同じデバイスでほかの APO と同時には使えません。
- APO を入れる・外すたびに Windows Audio を起動し直すので、数秒ほど音が止まります。
- 入れた直後の最初の再生だけ、アプリ側で「デバイスが無効になった」というエラーになることがあります。再生し直せば鳴ります。
